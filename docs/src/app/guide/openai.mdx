# OpenAI Assistants Integration

Contexta sits alongside the OpenAI Assistants API as the long-term memory layer that survives across threads.

## Installation

The adapter ships **inside** the `contexta-client` package in this repository. There is no separate `contexta-openai` distribution to install.

```bash
pip install -e clients/python
pip install openai
```

```ts
npm install ./clients/typescript openai
```

## Python

```python
from openai import OpenAI
from contexta_client import Contexta
from contexta_client.adapters.openai import contextaMemory, contextaAssistantRunner

openai_client = OpenAI()
client = Contexta.from_env()
memory = contextaMemory(client, user_id=ACTOR_UUID, token_budget=1500)
```

The constructor is `(client, user_id, token_budget=None, auto_batch_size=10)` — it takes a **`Contexta` instance plus a `user_id`**, not an OpenAI client and not keyword `user_id=`. There is no `from_env()` on the adapter.

### Fetch context, then run

```python
# Returns a {"role": "system", "content": "..."} dict
system_msg = memory.context_for_session(session_id)

run = openai_client.beta.threads.runs.create_and_poll(
    thread_id=thread_id,
    assistant_id=ASSISTANT_ID,
    additional_instructions=system_msg["content"],
)

# After the run, feed the thread back
messages = openai_client.beta.threads.messages.list(thread_id=thread_id)
memory.observe_thread(session_id, [{"role": m.role, "content": m.content[0].text.value}
                                   for m in messages.data])
```

Method names are `context_for_session(session_id)` and `observe_thread(session_id, thread_messages)`. There is no `context_for(user_id=..., query=...)` and no `observe_thread(user_id=..., session_id=..., messages=...)`; the adapter is already bound to the `user_id` you constructed it with.

### Drop-in runner

```python
runner = contextaAssistantRunner(openai_client, memory)

run = runner.run_with_session(
    assistant_id=ASSISTANT_ID,
    session_id=session_id,
    user_message="What do you know about me?",
)
```

The runner creates and caches a thread per `session_id`, prepends the Contexta context as a user message prefixed `[contexta Context]`, polls the run, and (with `auto_observe=True`, the default) observes the thread afterwards.

## TypeScript

```ts
import OpenAI from "openai";
import { Contexta } from "@contexta/client";
import { contextaMemory, contextaAssistantRunner } from "@contexta/client/adapters/openai";

const openai = new OpenAI();
const client = Contexta.fromEnv();
const memory = new contextaMemory(client, { userId: ACTOR_UUID, tokenBudget: 1500 });

const systemContent = await memory.buildSystemMessage(sessionId);

await openai.beta.threads.messages.create({
  thread_id: threadId,
  role: "user",
  content: userMessage,
});

const run = await openai.beta.threads.runs.createAndPoll(threadId, {
  assistant_id: ASSISTANT_ID,
  additional_instructions: systemContent,
});

const messages = await openai.beta.threads.messages.list(threadId);
await memory.observeThread(sessionId, messages.data);
```

TypeScript takes an **options object** (`{ userId, organizationId?, tokenBudget?, autoBatchSize? }`), which differs from the positional Python signature. Method names are `buildSystemMessage` and `observeThread`.

## What the adapter handles

- Translating OpenAI message content blocks into Contexta's `{role, content}` observation format
- Token-budgeted context injected as `additional_instructions` / a system message
- Caching the Contexta session id against the OpenAI thread id
- Batching observations (`auto_batch_size`, default 10)
- Swallowing and logging Contexta errors rather than failing the user's turn

## Gotcha

Every adapter needs a `user_id`, and **that user id must equal the actor bound to your API key.** `GET /v1/memories/context` is where the mismatch surfaces, as a `403`. The adapter cannot know your key's actor, so you have to pass the same value you minted the key with.
