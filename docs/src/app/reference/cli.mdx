# CLI Reference

The `contexta` CLI ships inside the `contexta-client` Python package (`clients/python`), as a Typer application.

## Installation

```bash
pip install -e clients/python
contexta --help
```

The package is not on PyPI yet, so `pip install contexta-client` will not work.

## Configuration

The CLI stores credentials in `~/.contexta/config.toml`:

```toml
[default]
api_url = "http://localhost:8000"
api_key = "mk_live_..."
org_id = "..."

[profiles.staging]
api_url = "http://localhost:8000"
api_key = "mk_live_..."
project_id = "..."
```

Use a profile with `contexta --profile=staging memories list`.

## What works against a v1.5 server

| Command | Description |
| :--- | :--- |
| `contexta login` / `logout` / `whoami` | Local credential management |
| `contexta init` | Scaffold `.env` and an integration snippet |
| `contexta test` | Smoke test: `ping`, `observe`, `context` |
| `contexta keys list` | `GET /v1/keys` |
| `contexta keys create` | `POST /v1/keys` |
| `contexta keys revoke` | `DELETE /v1/keys/{id}` |
| `contexta memories list` | Ranked memory list |
| `contexta memories show` | One memory |
| `contexta memories explain` | Scoring and supersession history |
| `contexta memories pin` | Pin a memory |
| `contexta memories archive` | Archive a memory |
| `contexta memories delete` | Delete a memory |
| `contexta observations send` | Send an observation from JSON or stdin |
| `contexta context get` | Context bundle |
| `contexta context preview` | Context with a sample query |
| `contexta audit` | Tail the audit log (`GET /v1/audit`) |
| `contexta export` | Export memories to JSONL |

## What returns 404 in v1.5

These subcommands still exist in the CLI but call endpoints that were removed. They will fail against a v1.5 server:

| Command | Dead endpoint | What to do instead |
| :--- | :--- | :--- |
| `contexta keys rotate` | `POST /v1/keys/{id}/rotate` | `keys create` then `keys revoke` |
| `contexta policies list` / `show` / `create` / `sync` | `GET`/`POST /v1/policies` | none — no policy registry |
| `contexta schemas list` / `create` | `GET`/`POST /v1/schemas` | none — no schema registry |
| `contexta projects list` / `create` / `use` | `GET`/`POST /v1/projects` | none |
| `contexta usage` | `GET /v1/usage` | none — there is no metering |

This is a client-side gap, not a server regression. The endpoints were removed with the billing and policy/schema subsystems; the CLI was never updated.

## Key scoping, and why the first key is special

`POST /v1/keys` is authenticated, so the first key on a fresh database has to be inserted directly into Postgres. The [quickstart](/quickstart) has the SQL, and it matches `ApiKeyRepository.create_key` exactly: `mk_live_` prefix, SHA-256 token hash, 16-character display prefix.

Once one key exists, use `contexta keys create` (or the console's **API Keys** page) for everything else.

**Remember that the key's actor is your `user_id`.** Sending a different one is a `403`, not an empty result. One key = one (organization, actor) pair.
