# Example: CRM Agent

A sales assistant that tracks contacts and deal context, scoped per contact.

## What it does

- Remembers contact details across interactions
- Recalls deal stage when a contact returns days later
- Keeps each contact's memory isolated from every other contact
- Surfaces the right follow-up without re-reading the whole transcript

## Full code

```ts
import OpenAI from "openai";
import { Contexta } from "@contexta/client";

const client = Contexta.fromEnv();
const openai = new OpenAI();

async function crmChat(
  apiKeyOrg: string,
  contactUserId: string,
  sessionId: string,
  message: string,
): Promise<string> {
  const ctx = await client.context({
    userId: contactUserId,
    organizationId: apiKeyOrg,
    sessionId,
    tokenBudget: 2000,
  });

  const systemPrompt = `You are a CRM assistant. Track contacts and deals.

Current context for this contact:
${ctx.toSystemPrompt()}

If the user mentions new contact details or deal updates, acknowledge the update.
Always confirm action items.`;

  const reply = (await openai.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [
      { role: "system", content: systemPrompt },
      { role: "user", content: message },
    ],
  })).choices[0]?.message?.content ?? "";

  await client.observe({
    userId: contactUserId,
    organizationId: apiKeyOrg,
    sessionId,
    messages: [
      { role: "user", content: message },
      { role: "assistant", content: reply },
    ],
    metadata: { agent: "crm-agent" },
  });

  return reply;
}
```

## Two isolation axes

`organizationId` is the tenant — one company, one deployment of this agent. `userId` is the individual being tracked inside it. Memories are scoped by both, so a rep looking at Acme Corp sees nothing about Globex.

The `apiKeys` row that authenticates the request also carries an `actor_id`, and that value is the `userId` the server will accept. So per-contact memory isolation is not a query parameter you can vary freely: **it requires one API key per contact**, because a `userId` that is not the key's actor returns `403`.

If you genuinely need one key to serve many contacts, that is a deliberate design change to the tenant model, not a configuration flag. For most CRM deployments — one rep, a bounded book of contacts — minting a key per contact is a one-off `POST /v1/keys` and the isolation is then enforced by the database rather than by your application code.

## What was removed, and why

The original version called `contexta.registerSchema({ name: "ContactInfo", fields: [...] })` twice, once for contacts and once for deal stages. **`POST /v1/schemas` does not exist** — the custom-schema registry was removed and `registerSchema()` raises `NotFoundError`.

The extractor already produces typed facts. A message like *"Alice Johnson is the CTO at Acme Corp, evaluating our API product at $50k, stage qualified"* becomes several typed memories with entity links between them, which is what the graph traversal channel reads on the next call.

```ts
// What actually works
await client.observe({
  userId: contactUserId,
  organizationId: apiKeyOrg,
  sessionId,
  messages: [
    {
      role: "user",
      content:
        "Alice Johnson is the CTO at Acme Corp, alice@acme.com. " +
        "They are evaluating our API product. Deal value $50k, stage qualified.",
    },
  ],
});
```

## A worked sequence

```ts
// Day 1
await crmChat(ORG, contactAcme, session1,
  "Alice Johnson is the CTO at Acme Corp. They're evaluating our API product. " +
  "Deal value: $50k, stage: qualified.");

// Day 2, a different session
const reply = await crmChat(ORG, contactAcme, session2,
  "What do I know about Acme Corp and what should I follow up on?");
// "Acme Corp is evaluating our API product ($50k, qualified stage).
//  Alice Johnson is the CTO. Suggested next action: send the technical spec."
```

The second call hits a different session and never sees the first transcript. It gets the memory anyway.

## Key takeaway

Use `organizationId` for the tenant and `userId` for the tracked party, and mint a key per `userId` so the isolation is enforced by the schema rather than by a filter in your code.
